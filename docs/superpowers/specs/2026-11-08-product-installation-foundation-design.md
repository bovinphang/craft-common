## 1. 意图与已确认边界

统一 frontend-craft、backend-craft 的产品安装底座，把稳定的产品无关机制抽入 craft-common，减少重复维护；同时使语言、框架与应用领域分别描述，让桌面、全栈、服务端及混合仓库能够组合使用专业能力。

- 保留三个仓库与现有产品；能力按领域确定唯一维护来源，允许跨产品消费。
- 不能将 Rust、Go、Java、Python、C、C++ 绑定为后端语言；桌面及全栈项目同样可能使用它们。
- 任务按子工程、语言、框架、运行位置和任务证据选择能力。

下文的首批迁移清单、框架名单、兼容策略及交付顺序是设计者的具体建议，随本文批准后才成为实施范围。此前讨论的“每种语言对应一个服务端框架”不作为范围依据。

## 3. 目标、非目标与失败判据

### 目标

1. 安装机制唯一维护，产品只声明身份、内容、产品策略及必要转换。
2. 现有安装、更新、卸载、dry-run、用户修改保护和跨产品共存有明确兼容路径。
3. 跨领域语言与桌面框架能力可随任一产品交付，不要求安装另一整个产品。
4. 同一仓库可包含 UI、桌面核心、原生库、服务；能力推荐基于任务证据，而非产品名或语言猜测。
5. 每个专项有独立入口、双语正文、正反触发样例、闭合资源和实际验证边界。

### 非目标

- 不创建第四个仓库、fullstack-craft、统一新 CLI 或面向所有框架的代码生成器。
- 不把所有工程能力搬到 common；UI、数据及服务端语义仍由领域产品维护。
- 不新增通用插件发现系统、依赖求解器、公共内容子集安装或按任务动态下载 Skill。
- 不整体重写十五个 Runtime 转换器，不自动启用新 Hooks，不改变 CLI 自更新产品策略。
- 不保证两个原生插件同时安装时的宿主发现与去重；仍需专项验证。
- 不自动下载编译器、执行未授权的工程命令、发布、推送或部署。

### 失败判据

公共正文仍跨仓库手工维护；common 反向依赖产品；把所有 Rust 工程视为服务端；只迁 SKILL.md 丢失资源；语言入口保留强制 HTTP/数据库分层；安装顺序影响结果；卸载一个产品损伤另一个；覆盖用户改动；dry-run 写入或触发恢复；以文件存在代替宿主激活或实际测试成功。

## 4. Approaches：比较与选择

| 方案 | 做法 | 权衡与决定 |
| --- | --- | --- |
| A：共享底层工具 | 只抽路径、哈希和文件工具 | 改动少，但生命周期、所有权和配置处理继续重复；未选择 |
| B：公共引擎与产品声明 | 统一机制，领域产品声明内容及策略 | 兼顾维护成本与产品差异；用户已选择 |
| C：完整统一 CLI/适配器 | 产品完全变成平台配置 | 初期范围与兼容风险过大，容易固化历史产品约束；未选择 |

能力组织采用多维描述，不增加“语言属于哪个产品”的独占映射。领域是维护职责，产品是组合交付入口。实现是一个跨仓库项目，分两个依次验收的阶段：安装机制统一；跨领域内容及框架能力。第一阶段未稳定前不迁移大批内容。

## 5. 三仓职责与依赖方向

| 仓库 | 唯一维护内容 |
| --- | --- |
| craft-common | 安装机制、公共研发方法、跨领域语言基础、进程/原生集成与首批桌面框架 |
| frontend-craft | UI、交互、渲染、可访问性、Web 框架与产品模板/Hooks/CLI 体验 |

首期两个产品均交付完整且相同的公共 Skill 目录，沿用现有完整摘要及消费者账本。按任务选择是推荐/使用行为，不是裁剪安装文件；不为减少已安装 Skill 数量重写公共共享协议。

## 6. 公共安装引擎

### 6.1 公共机制与产品声明

概念上提供 ProductDefinition、RuntimeDescriptor、InstallSession、InstallPlan 和 InstallResult；最终命名及目录拆分留给实施者。

- ProductDefinition：包名、资源前缀、命令标识、版本、清单位置、事务状态位置、配置条目标记、内容提供者及转换扩展。所有身份均显式传入并验证，公共包不得通过字符串替换猜测身份。
- RuntimeDescriptor：宿主标识、local/global 路径及环境变量规则、各类资源目标、宿主格式限制。产品另行声明自己交付的资源与启用策略；宿主支持和产品交付不混为一张布尔表。
- InstallSession：显式上下文和暂存读写、哈希前置条件、所有权及共享配置记录。会话实例之间无模块级可变状态；同一会话只允许顺序规划。独立会话可以并存，提交受目标锁协调。
- InstallPlan：创建、替换、删除、保留、冲突、人工步骤和公共引用变化。计划只读；提交时在锁内复核前置条件。
- InstallResult：统一内部结构，CLI 分别适配现有文字、JSON 与退出码；不借此次抽取静默改变对外命令契约。

产品只提供源文件、目标映射及生成内容，不直接写盘。前端既有转换器可通过兼容包装器逐个接入显式会话，不要求一次性重写全部生成逻辑。完成后包装器只委托公共机制，不再保留独立安装算法或全局草稿状态。

### 6.2 本期抽取范围

1. 目标路径与环境目录规则：保留现有特殊路径和优先级，用显式 home/env 输入便于测试；历史差异先通过夹具记录，不能未经报告统一成某一方默认值。
2. 产品写入规划与读己之写、文件摘要、根边界、普通文件及链接检查。
3. 产品文件所有权及安装/更新/部分卸载机制，通过兼容读写适配原清单。
4. JSON 字段/Hook、TOML 项、带身份标记文本的配置合并与精确移除，保留用户及其他产品条目。
5. 生命周期协调：公共目标存在时使用既有共享事务协调产品与公共账本；无公共目标时复用参数化产品事务。两种路径均在 common 唯一实现。
6. 内容快照同步中相同的资源收集、锁校验、旧文件保护及索引合并机制；产品保留领域方法嵌入映射和历史迁移映射。

CLI 交互、包管理器自更新/自卸载、领域规则生成、Hooks 的业务行为和项目命令执行器保留在产品侧。公共源码中不得出现运行时专属的 fec/bec 模板正文；迁移测试夹具允许保留历史样例。

### 6.3 安全与恢复不变量

- dry-run 不写目录、锁、日志、清单或快照；如存在待恢复状态，报告阻塞而不修复。
- 未知或修改过的文件不覆盖；未知配置不认领整文件。更新/卸载只操作已认领且仍匹配的文件或条目。
- 路径校验包含 Windows 大小写、真实祖先路径、允许根 junction 和根内链接拒绝；不把产品声明的根自动扩大到整个 home。
- 部分卸载保留残余所有权与公共消费者引用；最后一个消费者仅清理未修改的公共资源。
- 沿用既有公共目标锁，并对实际共享配置目标协调跨产品锁；即使公共 Skill 目标不同或不存在，也不能并发覆盖同一配置。多把锁按规范化键的固定顺序获取，避免锁顺序反转；锁的实现格式由实施者确定，必须验证竞态与中断释放。
- 锁内重新读盘、重新规划并验证哈希；恢复仅信任调用者声明的根及已验证身份。大日志和进程中断继续覆盖；不扩大为断电持久性或多主机保证。

## 7. 清单与名称迁移

首期保留 frontend-craft.manifest.json、后端清单位置、产品身份、共享账本格式和各 CLI 入口。公共引擎使用统一内存表示，产品侧只保留薄的历史清单编解码适配，不强迫存量用户先重装。

安装机制抽取阶段不改公共 Skill 名称及正文；先分别验证旧产品安装 -> 新引擎更新 -> 卸载。目录摘要包含包版本，版本变化即使正文不变也可能触发公共冲突，仍遵循下述协调升级规则；不能以“只改引擎”声称新旧公共包可以共存。必要时只能在计划中显式升级产品清单，不能让旧清单同时成为另一产品的所有权记录。

内容更名阶段采用明确旧名 -> 新名映射，不假设宿主存在通用 Skill 别名。仓库引用、agents、commands、规则、metadata、relations、评测及打包清单一起更新；旧入口不长期作为第二份自动发现入口保留。

- 只自动退役来源产品清单认领且哈希未变的旧目录，退役与新公共部署纳入同一事务。
- 旧目录存在用户修改、额外未知文件、链接或所有权不明时，写入前停止并给出迁移项；用户自行整合后重试。
- 对缺少标准 Skill 安装能力的 Runtime，也检查托管规则/转换文本中的旧引用；不假造其 Skill 支持。
- 新旧公共版本仍要求精确匹配。本期不提供跨版本消费者滚动升级或自动卸载另一个产品：双产品用户先用旧版本分别卸载、处理保留改动，再安装匹配的新产品组合；指南写明顺序。清单可读写兼容不等于可以跨公共摘要原位共存；此限制适用于两个阶段。
- 旧产品命令中受支持的领域入口不做机械替换；新增只读迁移报告复用现有检查机制，报告不回显用户文件整行。

## 10. 多维识别与能力组合

### 10.1 模型及公共边界

在 common 中复用并抽取已有只读工程扫描的通用机制，描述 ProjectUnit：根目录、语言证据、框架及版本证据、运行角色、构建入口、警告及扫描完整性。既有 backend Project/Inspection 对外 JSON 保持原有字段语义，通过适配新增可选信息；现有消费者不能因新的分类枚举而失效。

跨领域扫描器不执行工程命令、不安装依赖、不读取敏感配置内容。内置通用语言/清单及 Electron/Tauri 证据；前后端各自注册框架与领域检测规则，common 不导入产品。检测输出只含技术事实与来源，不含强制 Skill 选择。

为能力目录补充可校验的可选 applicability 字段：languages、frameworks、roles、taskKinds。维护来源由 sourcePackage 决定，产品交付由组合目录决定；不将 AI 宿主 platforms 与应用运行角色混用。继续使用现有 metadata/relations/eval_queries，避免另建竞争目录。

### 10.2 选择规则与对外入口

- 推荐先定位任务所属最近子工程；语言/框架需清单、依赖或明确源码证据。多模块关系保留，不给整个仓库指定唯一语言或角色。
- Rust、Python、C++ 等语言存在本身不证明是服务端；证据不够时角色为 unknown。桌面应用可同时具有 UI、desktop-core、native-library 等角色。
- 跨边界任务组合能力，例如 React 页面 + Tauri command 的 IPC 调整同时推荐 UI、Tauri 和 Rust；只改样式不加载所有 Rust 专项。
- 标签匹配只是候选推荐，不自动运行 Skill、命令或下载。description 及正反评测承担宿主自然触发约束，不能声称各宿主遵循同一中央路由器。
- backend 的 bec project inspect 保持兼容并接入公共检测；前端新增 fec project inspect 的只读入口，支持任务路径及 JSON，以相同事实模型服务混合项目。现有 OpenClaw 框架提示可委托该机制。
- CLI inspect 输出事实、候选能力 ID、理由、警告和完整性，不默认输出命令参数/环境值，不自动执行验证。候选仅来自该产品已经交付的目录，不跨产品凭空推荐未安装入口。
- backend 的 bec validate 继续使用已有执行器；本期不为前端新增跨语言自动执行器，也不把语言检查命令放进安装器。

## 11. 分发、版本与迁移交付

- 保留精确 common 依赖及生成快照。公共目录更名、新增或正文变化后，三个仓库的锁、摘要、metadata、关系及独立包清单必须同步。
- common 原有导出保留兼容；新增公共接口不移除旧协议。内部内容目录格式如需扩展，应使用可选字段或显式 schema 适配，不能假装旧锁已经包含新资源。
- 具体候选版本号在实施计划中依据实际发布状态确定；两个产品必须使用同一精确 common 候选版本，不实际发布。
- 本地包联调沿用 pnpm pack 和已有临时本地 registry，不依赖相邻源码路径，不改用户全局 registry；锁中临时地址不得混入待发布产物。
- npm CLI、Claude/OpenClaw 单产品包、独立 Skill 包分别验证完整性。双原生产品去重继续不在保证范围内。
- 为三个仓库更新职责说明、消费指南、旧名迁移表、框架清单、工程识别与验证边界。独立 Skill 的许可/来源信息保持可追溯。

## 12. 验收与阶段顺序

### 阶段一：安装引擎统一

先固定既有行为夹具；实现 common 显式会话和机制，分别迁移两个产品；转换器、CLI 输出和清单兼容都要验证。此阶段不同时迁移语言入口。

| 检查面 | 必须证明的行为 |
| --- | --- |
| 十五个 Runtime | 两产品 local/global 目标、能力及人工步骤不退化；en/zh-CN 内容有效 |
| 生命周期 | 首装、重复安装、更新、dry-run、卸载、部分卸载符合原契约 |
| 共存 | 前后端安装顺序互换；同版本共同使用；单方卸载；版本/语言/摘要冲突无写入 |
| 配置 | 两产品与用户 JSON/TOML/文本条目共存；修改后保留；并发计划拒绝失效前置条件 |
| 恢复与边界 | 中断、大日志、错误身份、越界、链接、junction、Windows 大小写及无公共目标的事务 |
| 维护结果 | 产品不再维护第二份规划、事务、配置合并及生命周期算法 |

### 阶段二：能力边界与框架交付

完成十二项迁移、七个专项、多维识别及两个 inspect 接入；更新引用、双语、来源锁与所有渠道。

工程夹具至少包含：React+Tauri；Electron main/preload/renderer；C 库+Rust FFI；UI+独立服务的混合仓库；普通 Rust 库反例；Python CLI 反例；无关包名/仅源码字符串反例；缺清单、版本不明、缺工具及扫描截断。

专项内容以版本匹配的官方资料为依据。每个新框架应有微型工程或明确的自动检查夹具证明核心行为，至少覆盖一个框架特有缺陷及修复；具备真实工具链时才记录运行通过。需要图形桌面、平台签名或外部数据库的验证分别列出，不能用静态内容检查代替。缺少环境记为未验证，并在交付中明确，不把七个专项描述成全部平台已验收。

每仓按实际 scripts 执行 pnpm lint、pnpm typecheck、pnpm build、pnpm test；backend 新 checkout 需先 build 再 test。另执行 common 同步校验、独立包、原生包及共存专项的既有命令。仅设计文档阶段做文档与差异检查，不把历史测试报告作为本次通过证据。

## 13. 留给实施者的决定与风险

实施者可决定模块文件名、内部接口命名、测试夹具布局、迁移分批粒度和跨产品共享锁具体文件格式；不能自行扩大首批框架、改变公共目录子集策略、取消兼容保护或声称原生双产品去重。

主要风险：公共目录扩大带来宿主发现噪声；语言正文中隐藏服务端前提；历史清单与配置所有权差异；公共摘要升级需要双产品协调；跨平台桌面测试环境不足。分别用明确 description/负例、逐项内容审查、旧安装夹具、明确升级顺序和分层验证报告控制。

仓库 Git 约定要求未经用户确认不直接 commit，因此本文先作为可审阅工作区文件保存，不提交、不发布。批准后下一步使用 writing-plans 生成实施计划；设计批准不视为已经运行校验或完成实现。
