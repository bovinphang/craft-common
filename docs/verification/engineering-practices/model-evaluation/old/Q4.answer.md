建议把最小改动限定在公共契约、初始化和资源生命周期，保持现有 JDK、Python 版本及依赖体系，不引入 Web 框架。

1. **按实际职责划分边界。** Java/Python 库保留公共 API、领域逻辑和外部资源适配；CLI、桌面入口负责参数转换、启动和错误展示。有真实持久化职责时再使用 repository。先核对现有包结构和依赖方向，复用已有实现，不为统一名称强制套用 controller/service/repository。

2. **Python 导入保持无外部副作用。** 将连接创建移至明确工厂、上下文管理器或调用方启动阶段；领域计算通过参数接收依赖。导入包、读取版本或使用纯计算功能应不依赖外部服务。已有调用方式受影响时，应明确迁移方式和兼容范围。

3. **Java 初始化失败保留原始原因。** 初始化应成功返回可用对象，失败则按现有契约抛出异常并保留 cause，不能吞错返回空对象。CLI、桌面调用方决定退出、重试或禁用相关功能；若允许部分功能启动，须显式表示不可用状态，避免把初始化失败伪装为成功。库本身不终止调用方进程。

4. **处理失败前已创建的资源。** 列明文件、客户端、线程池等资源的创建方和关闭方。初始化失败时，按获取顺序的逆序关闭本次拥有的资源；调用方借入的资源仍由调用方负责。清理失败不得覆盖初始化原异常，应按现有异常约定保留附加错误。正常关闭、重复关闭及失败后重试的行为也要明确。

5. **验证先覆盖可隔离的公共行为。** 后续在获允许运行的既有环境中，使用项目现有测试工具验证：Python 导入不连接服务；非法输入；各资源获取阶段失败；原异常原因保留；资源关闭顺序与次数；借入资源不被关闭；重复调用及重试符合契约。fake 可验证调用和清理行为，不能证明真实服务连接、事务或驱动关闭语义。

6. **据实记录验证限制。** 实施前核对 Java 构建文件、wrapper、声明版本，以及 Python 的 pyproject、锁文件、支持版本和检查配置；随后执行仓库已有 lint、类型检查、测试及构建命令。本轮仅依据所附材料评审，未读取实际工程、未执行项目检查。当前缺少 JDK、外部服务和运行权限，编译、测试及真实服务失败恢复均未验证；不自动安装工具、下载 wrapper 依赖或升级运行时。仅有异步或性能问题证据时，再引入对应专项诊断。
