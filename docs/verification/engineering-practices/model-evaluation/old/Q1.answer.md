应调整赶工要求：付款不能仅凭429、5xx或网络错误自动重放，类型断言也不能证明响应有效。沿用 React、TypeScript、pnpm、node:test，在现有请求封装、付款 API 和业务 Hook 内做最小修改。

1. **付款先明确结果，再决定重试。** 默认关闭付款自动重试。超时、断网、取消只表示客户端未取得结果，不能证明服务端未提交。进入“结果待确认”，阻止重复提交，按订单或操作标识查询；轮询须有次数、总时限和终态停止条件。没有查询能力时提供核对或支持入口，不能引导用户直接再次付款，也不能把未知结果当作失败回滚。

2. **写操作重试必须有服务端保证。** 与后端确认幂等键、原子去重、相同键重放原结果、载荷不一致时拒绝、有效期及状态查询契约。同一次付款意图的所有尝试复用同一键和载荷，不能每次重试生成新键。按钮防连点不能替代服务端幂等。契约未落实前，保留禁止自动重放的边界；人工重试同样受此限制。

3. **把重试收敛到一层。** 仅对明确可安全重放的操作，按错误类别允许重试：429遵守有效的 `Retry-After`，可恢复的5xx和网络错误使用指数退避加抖动，限定总尝试次数及总耗时。等待也须可取消。业务4xx、响应校验失败、主动取消不自动重试；避免请求层与 Hook 叠加重试。材料中的通用重试建议不能覆盖付款语义。

4. **取消与过期响应防护同时做。** Hook 每次请求建立 `AbortController` 和递增请求代号，参数变化、卸载时取消请求、退避等待及轮询，并使旧代号失效。成功、失败及 `finally` 更新状态前都检查代号，防止A覆盖B或清掉B的 loading；即使底层忽略取消也有效。区分超时与主动取消，取消不展示普通错误。付款由明确的用户事件触发，避免放进挂载 Effect。

5. **运行时校验替代断言。** JSON和捕获异常均从 `unknown` 开始，通过已有 schema 或类型守卫校验，再映射 DTO 与领域模型；泛型 `requestJson<T>` 或 `as T` 不构成校验。明确204、空体、非JSON、非法枚举及错误体行为；付款响应损坏仍可能已经提交，应转入待确认。用判别联合表达提交中、待确认、成功、明确失败，日志保留请求标识并脱敏。请求失败进入可恢复 UI，渲染异常才交给 Error Boundary。

6. **使用现有 node:test 验证关键行为。** 注入请求函数、时钟和等待函数，用可控 Promise 覆盖：服务端提交后客户端超时不会重复付款；幂等重放与载荷冲突；重试次数、退避及取消；A晚于B返回成功或失败，旧 `finally` 不影响B；卸载后无更新和遗留定时任务；非法响应、204及非JSON错误。后续核对 `package.json`，执行已有 lint、类型检查、测试和构建脚本。
