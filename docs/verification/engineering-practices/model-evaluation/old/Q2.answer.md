建议不采纳这项赶工方案。增大 channel 缓冲只能推迟阻塞；`Arc` 延长共享资源生命周期，不能证明任务结束；丢弃任务句柄会失去等待和错误传播能力。只发 cancel 就返回，无法保证锁已释放、文件已收尾或后台工作已停止。

1. **先确认最小范围。** 实施时定位所属 Go 模块、Rust crate、运行时版本及现有关闭入口，列出各任务的创建方、阻塞点、取消方式、资源拥有者和等待方。改动限于这些生命周期代码及相关测试，保留模块路径、依赖、edition 和 MSRV，不重构 workspace。

2. **修复 Go 退出链。** 停止接单后，按业务契约选择排空队列或取消未完成工作。阻塞发送应同时监听 `ctx.Done()`，接收和下游 I/O 也应能结束；消费者提前退出时，生产者不能永久卡住。创建方用现有等待机制确认全部 goroutine 退出。多生产者由协调方等待所有发送结束，再关闭 channel；消费者不能擅自关闭，不用 `recover` 掩盖发送/关闭竞争。避免持锁等待 channel、I/O 或任务退出。

3. **修复 Rust 任务和资源管理。** 保留任务句柄，限制队列与在途任务，传播任务错误和 join 失败。只有确需共享生命周期的资源才用 `Arc`；缩小锁守卫作用域，避免持阻塞锁跨 `.await`。不可避免的阻塞工作放入现有运行时支持的有界执行边界。关闭时停止接单，发出取消或排空请求，再等待句柄完成。超时、丢弃 future 或 abort 都不能统一视为底层操作停止；须按实际操作确认取消安全。文件短写或取消可能留下部分进展，应明确记录进度、恢复、回滚或幂等重试规则，完成必要 flush/关闭并传播错误。

4. **明确库与桌面边界。** 库管理自己创建的任务和资源，提供可等待、可重复调用的关闭接口，并返回失败或未完成状态；不直接退出进程或操作窗口。桌面组合根协调 Go/Rust 两侧关闭、总期限和用户提示，两侧完成后再释放共同依赖。期限耗尽须报告未完成工作；强制退出策略由桌面层决定，不能宣称清理成功。

验证应使用屏障、可控事件和失败注入，覆盖队列饱和、消费者提前退出、并发/重复关闭、持锁等待、取消写入、短写和下游失败；断言任务均结束、资源可释放、错误可观察及文件状态符合恢复契约。按现有脚本在变更 Go 模块执行格式检查、vet、定向测试及 race 检查；在相关 Rust crate 执行 fmt 检查、clippy 和定向测试。重复启停时核对任务、栈及文件句柄是否持续增长，有限测试不能证明所有交错安全。
