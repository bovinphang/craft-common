付款应停用无条件三次重试，响应应经过运行时校验。沿用现有 React、TypeScript、pnpm、node:test，复用请求层和业务 hook，控制改动范围。

1. 在 API 边界以 `unknown` 接收响应和错误，用既有 schema 或类型守卫校验，再转换为领域值。明确金额单位、有效范围、状态枚举、空体及失败输出；非法请求输入在发送付款前拒绝，坏响应不得触发成功回调。`as Payment`、`requestJson<T>`和生成类型都不能替代运行时校验。保留原始原因和脱敏关联 ID，不吞错返回空成功对象。

2. 将“失败”与“提交结果不确定”分开，用判别联合表达提交中、待确认、成功、失败。超时、断网、取消及响应解析失败都可能发生在付款提交之后，不能据此显示“未扣款”或虚构服务端回滚。无安全重放契约时保持待确认，通过已有订单/操作查询核对权威状态；缺少核对能力则提出协作需求并提供支持入口，不猜测端点或字段。

3. 只有服务端保证稳定幂等契约后才允许付款重放：首次发送前确定意图与键，重试沿用同键同意图；服务端需保证并发去重、副作用与结果的原子记录、结果复用、不同意图冲突及有效期。禁按钮、前端内存去重、换新键和 Abort 都不能提供此保证。安全读取与写入分别配置；允许的重试只在一层执行，限制次数、总截止时间，采用抖动退避，安全前提内才遵守 `Retry-After`，取消时停止后续尝试。

4. 对只展示最新结果的视图，按组件或完整 query key 管理请求身份、代次和寿命；成功、错误以及 `finally` 更新 loading 前全部检查当前身份。依赖变化或卸载时先使旧任务失效，再取消自己拥有的请求、定时器、监听和重试等待。保留并处理所属 Promise；发出取消不等于任务退出。共享缓存由原拥有者管理，卸载只解除本消费者订阅，不能取消其他消费者；独立付款命令也不能套用“只留最新结果”而丢失核对责任。

5. 普通请求失败进入可恢复 UI，渲染异常才交给 Error Boundary。付款确认成功后再更新或失效相关缓存；待确认时核对状态，不把乐观界面恢复解释为付款已撤销。
